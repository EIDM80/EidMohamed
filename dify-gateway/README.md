# بوابة Dify — طبقة تعدد المستأجرين

خدمة تقف أمام نشر Dify واحد بمساحة عمل واحدة، وتحوّله إلى أساس صالح لـ SaaS.

عملاؤك يخاطبون هذه الخدمة فقط. لا يصلون إلى Dify، ولا يملكون فيه مساحة عمل، ولا يعرفون أنه موجود.
وهذا ما يبقي الاستخدام داخل ما تسمح به رخصة Dify: `a backend service for other applications`.

## القاعدة الحاكمة

> **هوية المستأجر لا تأتي من العميل. أبداً.**

تُقرأ من رمز الجلسة، ثم تُحقن في حقل `user` عند نداء Dify بالصيغة `<tenant_id>:<user_id>`.
داخل سير العمل تصل كمتغيّر نظامي `sys.user_id`، وهو ما يطابقه مرشّح الوسوم على قاعدة المعرفة.

لا يوجد في `app/schemas.py` أي حقل يقبل `tenant_id` من المتصل. اختبار يرسل طلباً عدائياً كاملاً ويتأكد من ذلك.

## البنية

| الملف | المسؤولية |
|---|---|
| `app/models.py` | جداولك: المستأجرون، المستخدمون، الربط بـ Dify، المستندات، الحصص، الاستهلاك |
| `app/deps.py` | استخراج المستأجر من الجلسة، والتحقق من قاعدة البيانات في كل طلب |
| `app/dify.py` | **الوحدة الوحيدة التي تعرف Dify** — احتواء متعمّد يبقيه قابلاً للاستبدال |
| `app/plans.py` | الباقات وحدودها — المكان الوحيد الذي يجيب «ماذا تسمح هذه الباقة» |
| `app/usage.py` | فحص السقف قبل الإنفاق، وتسجيل الاستهلاك بعده |
| `app/ratelimit.py` | تحديد المعدّل لكل مستأجر — غير موجود في نسخة Dify المجتمعية |
| `app/observability.py` | معرّف لكل طلب، سجلّات JSON، وأخطاء لا تسرّب شيئاً |
| `app/routers/chat.py` | نقطة الدخول للعميل، بنمطَي رد: كامل ومتدفّق |
| `app/routers/documents.py` | رفع المعرفة ووسمها بالمستأجر |
| `app/routers/conversations.py` | سجل محادثات العميل — قوائم، تسمية، حذف |
| `app/routers/billing.py` | استقبال أحداث الاشتراكات وتغيير الباقة تلقائياً |
| `app/billing.py` | التحقق من توقيع الـ webhook وخريطة الأسعار |
| `app/routers/admin.py` | إنشاء المستأجرين، تغيير الباقات، تصدير الفوترة |
| `app/routers/ops.py` | `/health` للحياة و`/ready` للجاهزية — سؤالان مختلفان |
| `app/static/index.html` | لوحة تحكم العميل، لا تذكر المحرّك ولا تحمل مفتاحه |

## التشغيل

```bash
make install
cp .env.example .env          # عدّل GATEWAY_SECRET_KEY و DIFY_BASE_URL
make migrate
make seed name="Acme" email=you@example.com key=app-xxxxx
make dev
```

التوثيق التفاعلي على `http://localhost:8000/docs`.

```bash
# الدخول
curl -s localhost:8000/api/auth/login -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"..."}'

# سؤال
curl -s localhost:8000/api/chat -H "Authorization: Bearer <TOKEN>" \
  -H 'content-type: application/json' -d '{"query":"ما سياسة الاسترجاع؟"}'

# رفع مستند
curl -s localhost:8000/api/documents -H "Authorization: Bearer <TOKEN>" \
  -F file=@policy.pdf
```

ثم افتح `http://localhost:8000/app` — لوحة التحكم جاهزة: دخول، محادثة متدفّقة، رفع مستندات، وعدّاد استهلاك.

بـ Docker: `make docker` — البوابة وPostgres وRedis، والهجرات تُطبَّق عند الإقلاع.
للإنتاج: `make secrets && make prod` — يضع Dify على شبكة داخلية، ويحوّل الأسرار إلى ملفات، ويقيّد المنفذ على `127.0.0.1`.

## ربط العزل داخل Dify

خطوتان لمرة واحدة على تطبيق Dify:

1. **حقل البيانات الوصفية** — البوابة تنشئ حقل `tenant_id` تلقائياً عند أول رفع، وتضع فيه معرّف المستأجر.
2. **عقدة استرجاع المعرفة** — فعّل `metadata_filtering_mode: manual` وأضف شرطاً:

   | الحقل | القيمة |
   |---|---|
   | الاسم | `tenant_id` |
   | المُقارِن | `is` |
   | القيمة | `{{#sys.user_id#}}` |

قيمة الشرط تمرّ في Dify عبر `convert_template`، أي تُحلّ وقت التنفيذ من الطلب نفسه.
فتحصل على قاعدة معرفة واحدة تخدم مئات العملاء، ولا يرى أحدهم مقاطع الآخر.

### الحارس الآلي

هذا العزل مفروض في **إعداد سير العمل**، لا في قاعدة البيانات — نشرة خاطئة واحدة تُسقط الجدار.
لذلك صدّر الـ DSL إلى `workflows/` وشغّل:

```bash
make check-workflows
```

يرفض أربع حالات: الترشيح معطّل، أو على حقل آخر، أو بقيمة ثابتة بدل `{{#sys.user_id#}}`،
أو بـ `contains` بدل `is`. وهو خطوة إلزامية في `.github/workflows/gateway.yml`.

للعملاء الحسّاسين استخدم باقة `enterprise` — تنشئ قاعدة معرفة مستقلة، فيصير العزل في مستوى التخزين لا الإعداد.

## طبقات العزل الأربع

| الطبقة | الآلية | يحرسها |
|---|---|---|
| الجلسة | `tenant_id` من الرمز لا من الجسم | `test_isolation.py` |
| المحادثات | حقل `user` ← سجل `EndUser` في Dify | `test_isolation.py` |
| المعرفة | وسم `tenant_id` + مرشّح `{{#sys.user_id#}}` | `test_documents.py` + `check_workflow_dsl` |
| ملكية المستندات | جدول `documents` عندك لا قوائم Dify | `test_documents.py` |
| سجل المحادثات | Dify يحصر النتيجة على `EndUser` المرسَل | `test_conversations.py` |

الطبقة الرابعة تستحق تفسيراً: نقطة قوائم Dify تُرجع كل ما في قاعدة المعرفة.
الاعتماد عليها كان سيسمح لمستأجر بتعداد ملفات غيره أو حذفها بتخمين المعرّف،
فالبوابة تحتفظ بجدول ملكية خاص بها وتصرّح كل قراءة وحذف منه.

## الاختبارات

```bash
make test    # 65 اختباراً
```

`test_isolation.py` و`test_documents.py` و`test_conversations.py` تحرس الثابت الذي تقوم عليه المعمارية.
**فشل أي اختبار فيها يعني تسرّب بيانات بين العملاء، ويوقف الإصدار.**

و`test_billing.py` يحرس المال: توقيع مزوّر، حمولة معدّلة، وتوقيع معاد من الأمس — كلها مرفوضة باختبار.

## الفوترة

`POST /api/billing/webhook` يستقبل أحداث مزوّد الدفع ويحرّك الباقة تلقائياً.
ثلاثة ضمانات مبنية فيه:

| الضمان | لماذا |
|---|---|
| التحقق من التوقيع قبل أي تحليل | حدث مزوّر يرفع باقة مجاناً |
| فحص الطابع الزمني (٥ دقائق) | توقيع صحيح من الأمس هو إعادة تشغيل |
| معرّف كل حدث يُطبَّق مرة واحدة | المزوّدون يعيدون الإرسال، وإعادة تطبيق ترقية أو تخفيض خطأ |

الربط يحتاج `billing_customer_id` عند إنشاء المستأجر — بدونه لا يجد الحدث صاحبه.
وخريطة الأسعار في `BILLING_PRICE_MAP`، فإضافة سعر تغييرُ بيئة لا نشرُ كود.

> الحدث المُهمَل يُرد عليه بـ 200 عن قصد. المزوّدون يعيدون إرسال أي رد غير 2xx،
> وإعادة إرسال حدث لن نتصرّف فيه أبداً تملأ طابورهم بلا فائدة.

## التشغيل والتصليب

| الملف | ما يفعله |
|---|---|
| `docker-compose.prod.yml` | Dify على شبكة داخلية، أسرار كملفات، منفذ على `127.0.0.1` |
| `scripts/backup.sh` | نسخ قاعدة البيانات ومسح الأقدم من ١٤ يوماً — **بعد** نجاح النسخة الجديدة |
| `/ready` | يفحص القاعدة وDify، ويرد 503 إن سقط أحدهما |

`/health` و`/ready` سؤالان مختلفان عن قصد: الأول يقرّر إعادة التشغيل، والثاني يقرّر إرسال الحركة.
دمجهما يجعل انقطاع قاعدة البيانات يبدو كحلقة انهيار.

قاعدة بيانات البوابة هي النسخة الوحيدة من هوية عملائك واستحقاقاتهم وما عليهم.
Dify يُعاد بناؤه من نسخه، وهذه لا تُستعاد من شيء — فاجعل `backup.sh` مهمة مجدولة من اليوم الأول.

## لماذا `app/dify.py` وحدة واحدة

رخصة Dify تمنح مالكه حق تشديدها متى شاء. حصر كل ما يخصه في وحدة واحدة وجدول `dify_bindings`
يجعل الانتقال إلى محرّك آخر — RAGFlow مثلاً، وهو أباتشي 2.0 نقية — مسألة استبدال ملف،
لا إعادة بناء للمنتج. وهي معمارية أفضل بمعزل عن الرخصة: منتجك يملك عملاءه وبياناته ومنطقه.
