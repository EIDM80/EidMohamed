# بوابة Dify — طبقة تعدد المستأجرين

خدمة رقيقة تقف أمام نشر Dify واحد بمساحة عمل واحدة، وتحوّله إلى أساس صالح لـ SaaS.

عملاؤك يخاطبون هذه الخدمة فقط. لا يصلون إلى Dify، ولا يملكون فيه مساحة عمل، ولا يعرفون أنه موجود.
وهذا بالضبط ما يبقي الاستخدام داخل ما تسمح به رخصة Dify: `a backend service for other applications`.

## القاعدة الحاكمة

> **هوية المستأجر لا تأتي من العميل. أبداً.**

تُقرأ من رمز الجلسة الموثّق، ثم تُحقن في حقل `user` عند نداء Dify بالصيغة `<tenant_id>:<user_id>`.
داخل سير العمل تصل هذه القيمة كمتغيّر نظامي `sys.user_id`، وهو ما يطابقه مرشّح الوسوم على قاعدة المعرفة.

لا يوجد في `app/schemas.py` أي حقل يقبل `tenant_id` من المتصل — وهذا مقصود، وتحرسه اختبارات.

## البنية

| الملف | المسؤولية |
|---|---|
| `app/models.py` | جداولك: المستأجرون، المستخدمون، الربط بـ Dify، الحصص، الاستهلاك |
| `app/deps.py` | استخراج المستأجر من الجلسة، والتحقق من قاعدة البيانات في كل طلب |
| `app/dify.py` | **الوحدة الوحيدة التي تعرف Dify** — احتواء متعمّد يبقيه قابلاً للاستبدال |
| `app/usage.py` | فحص السقف قبل الإنفاق، وتسجيل الاستهلاك بعده |
| `app/ratelimit.py` | تحديد المعدّل لكل مستأجر — غير موجود في نسخة Dify المجتمعية |
| `app/routers/chat.py` | نقطة الدخول للعميل، بنمطَي رد: كامل ومتدفّق |

## التشغيل

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env          # عدّل GATEWAY_SECRET_KEY و DIFY_BASE_URL

python -m scripts.seed --name "Acme" --email you@example.com --app-key app-xxxxx
uvicorn app.main:app --reload
```

التوثيق التفاعلي على `http://localhost:8000/docs`.

```bash
# الدخول
curl -s localhost:8000/api/auth/login \
  -H 'content-type: application/json' \
  -d '{"email":"you@example.com","password":"..."}'

# سؤال
curl -s localhost:8000/api/chat \
  -H "Authorization: Bearer <TOKEN>" \
  -H 'content-type: application/json' \
  -d '{"query":"ما سياسة الاسترجاع؟"}'
```

## ربط العزل داخل Dify

بعد إنشاء المستأجر، خذ `tenant_id` المطبوع ونفّذ خطوتين في Dify:

1. **على المستندات** — أضف حقل بيانات وصفية اسمه `tenant_id` وقيمته معرّف المستأجر.
2. **على عقدة استرجاع المعرفة** — فعّل `metadata_filtering_mode: manual`، وأضف شرطاً:

   | الحقل | القيمة |
   |---|---|
   | الاسم | `tenant_id` |
   | المُقارِن | `is` |
   | القيمة | `{{#sys.user_id#}}` |

قيمة الشرط تمرّ في Dify عبر `convert_template`، أي تُحلّ وقت التنفيذ من الطلب نفسه.
فتحصل على قاعدة معرفة واحدة مشتركة تخدم مئات العملاء، ولا يرى أحدهم مقاطع الآخر.

> **تنبيه:** هذا العزل مفروض في **إعداد سير العمل**، لا في قاعدة البيانات.
> نشرة خاطئة واحدة تُسقط الجدار. اجعل نشر أي سير عمل يمرّ باختبار يتحقق من وجود المرشّح ومن ربطه بالمتغيّر النظامي.
> للعملاء الحسّاسين، استخدم قاعدة معرفة مستقلة عبر `DifyClient.create_dataset` واملأ `DifyBinding.dataset_id`.

## الاختبارات

```bash
pytest
```

`tests/test_isolation.py` يحرس الثابت الذي تقوم عليه المعمارية كلها — منها اختبار يرسل
`tenant_id` مزوّراً في جسم الطلب ويتأكد أن ما يصل Dify هو هوية الجلسة لا المزوّرة.
**فشل أي اختبار في هذا الملف يعني تسرّب بيانات بين العملاء، ويوقف الإصدار.**

## لماذا `app/dify.py` وحدة واحدة

رخصة Dify تمنح مالكه حق تشديدها متى شاء. حصر كل ما يخصه في وحدة واحدة وجدول `dify_bindings`
يجعل الانتقال إلى محرّك آخر — RAGFlow مثلاً، وهو أباتشي 2.0 نقية — مسألة استبدال ملف،
لا إعادة بناء للمنتج. وهي معمارية أفضل بمعزل عن الرخصة: منتجك يملك عملاءه وبياناته ومنطقه.
